# NutriGuard — Egyptian Recipe Manual‑Review Workflow (Step 3)

> **Status: Requirement.** Automated logic can never mark a recipe `verified`.
> Only the **Egyptian Recipe/Cultural Reviewer** may, with documented cultural
> evidence, reviewer identity, and a strict ISO review date
> (`MVP_REQUIREMENTS.md` §2.1, `DECISION_LOG.md` DEC-032).

## 0. Schema version

The staging registry uses **schema version `2.0`**
(`STAGING_SCHEMA_VERSION` in `src/domain/recipes.ts`). Records created under the
previous `1.0` schema are migrated automatically on every `npm run stage`:

- Missing v2.0 machine-owned fields (`sourceFingerprint`,
  `review.snapshotFingerprint`, `review.staleReason`, `review.staleCode`,
  timeline `evidenceIds`, `timeline.*Fingerprint`) are filled in from current
  raw data when possible.
- A `migrated_from_legacy` timeline entry is added for records that had no
  prior timeline.
- **Any previously `verified`/`rejected` v1.0 record whose latest human
  decision cannot be bound to a documented 64-hex `snapshotFingerprint` is
  routed back to `needs_review`** via a `migrated_cannot_bind_snapshot`
  pipeline event and tagged `review.staleCode = "legacy_snapshot_unbound"`.
  Its history is preserved, but the decision fields are cleared so the
  reviewer can re-bind the decision to the current raw snapshot (see §8,
  Drift lifecycle). No historical reviewed fingerprint is ever fabricated
  (`previousFingerprint`/`currentFingerprint` stay `null` for this event).

## 1. Where the registry lives

- **Registry (source of truth):** `data/staging/recipes.json` — generated by
  `npm run stage`, then curated by humans.
- **Primary import input:** `unified_egyptian_rag_database_v2_final.json`.
  It contains the graduation-project-approved recipes and their explicit human
  review log. The pipeline mirrors those documented decisions and never edits
  the source file.
- **Legacy fixture fallback:** when the unified file is absent (for isolated
  staging tests), the read-only recipe CSV under `data/raw/` follows the
  original classify-then-review workflow below.
- **Report:** `data/reports/recipe-verification-report.{json,md}` — current
  counts and blockers, regenerated on every `npm run stage`.
- **Evidence references:** `data/manifest/sources.json`
  (`egyptian_recipe_cultural_evidence` IDs are the only recipe‑eligible
  manifest evidence).
- **Source/license manifest:** `data/manifest/sources.json` also carries the
  *only* authoritative provenance + license review status for each source
  file. The staging registry never fabricates these fields by hand.

## 2. Import (automated, read‑only over raw)

`npm run stage` prefers the unified JSON source. A recipe enters staging as
`verified` only when its recipe status, matching `human_review_log` entry,
cultural reviewer identity/date, and HTTP(S) evidence URL are all present and
consistent. The source manifest must also approve provenance and license. The
legacy CSV fallback performs this deterministic classification:

Every verified review decision must also include a non-empty
`mealCategories` array containing one or more of `breakfast`, `lunch`, and
`dinner`. This is a human assignment made in `applyReviewDecision`; the pipeline
and Step 16 repository never derive it from raw `category` or `main_dish` data.

| Raw row condition | Result |
| --- | --- |
| Explicit Egyptian‑scope evidence (dish alias, explicit Egyptian cuisine, Egyptian main ingredient, “Egypt” mention) | Staged as `needs_review` with the original row preserved in `original` |
| Clearly non‑Egyptian (all declared cuisines non‑Egyptian, no Egyptian signal) | Staged as `rejected` (`review.autoRejected = true`) with the cuisine evidence recorded in the timeline |
| Malformed / missing title / missing ingredients | Excluded, counted in the report |
| No Egyptian evidence and not decidable | Excluded — never silently treated as Egyptian |

The pipeline never fabricates values: missing fields (`names.ar`, `region`,
`servings`, `finalCookedWeightG`, …) stay `null`; `license.status` stays
`not_assessed` or `pending` until a licensed source is reviewed in the
manifest.

Every imported row is fingerprinted canonically (see §3) and the digest is
stored in `sourceFingerprint`. This 64‑character lowercase hex digest binds
the staged record to the exact raw row it was built from.

`data/processed/cleaned_recipes.json` (the general‑purpose global recipe dump)
is **never** imported and is reported as ignored.

## 3. Provenance fingerprints — SHA‑256 row binding

Two distinct fingerprints are used; both are **exactly 64 lowercase
hexadecimal characters** (validated via `isSha256Hex` in `src/domain/recipes.ts`):

### `sourceFingerprint` (machine-owned, on the record)

- Set on every import by the pipeline from the raw row.
- Computed by `computeRowFingerprint(sourceFile, sourceRow, headers, row)`
  over the canonical columns: `recipe_title`, `description`, `category`,
  `subcategory`, `cuisine_list`, `main_ingredient`, `ingredients`,
  `ingredients_canonical`, `directions`.
- Cosmetic edits to non-canonical columns do **not** change the fingerprint
  and therefore do not trigger a false drift.
- Always required. A missing, empty, or non‑SHA‑256 `sourceFingerprint` is a
  validation error.

### `review.snapshotFingerprint` (human-owned, on the review block)

- **Only set by `applyReviewDecision`** when a human records a verdict.
- Copied from the record's `sourceFingerprint` at the moment of review so the
  review is cryptographically bound to the exact source snapshot the
  reviewer looked at.
- `null` before any human decision (including needs_review / auto-rejected).
- Required for any human verdict (`verified` or human `rejected`).
- If `review.staleReason` is non-null, `snapshotFingerprint` is cleared to
  `null` AFTER being preserved in the `source_drift_detected` timeline event,
  so that a subsequent re-review binds to the *new* fingerprint.

### `review.staleReason` and `review.staleCode`

`staleReason` is a human-readable string set when the record has been routed
back to review. `staleCode` is the machine-readable companion code that makes
the state queryable/auditable and drives the review policy. Exactly one of the
following three codes is set, and `staleReason` describes it:

| `staleCode` | Meaning | Reviewable? |
| --- | --- | --- |
| `source_changed` | The reviewed raw row changed in-place (canonical-fingerprint mismatch). The pipeline has already refreshed `original` + `sourceFingerprint` from the current row. | **Yes** — apply `applyReviewDecision` to re-bind to the new fingerprint. |
| `source_deleted` | The reviewed raw row is gone / the record is orphaned. `applyReviewDecision` **rejects** any fresh review, and eligibility blocks the record independently of hand-edited status/reviewer fields. | **No** — restore the raw row (or attach the record to a documented current source snapshot); the next `npm run stage` re-attaches it and downgrades the code to `source_changed`. |
| `legacy_snapshot_unbound` | A legacy v1.0 record could not be bound to a historical reviewed fingerprint (nothing is fabricated). | **Only when** a current imported source row and a valid computed `sourceFingerprint` are available, then `applyReviewDecision` may be applied. |

Any stale state blocks eligibility entirely, even when `verificationStatus`
was previously `verified`. A stale record is always paired with a
`source_drift_detected` or `migrated_cannot_bind_snapshot` pipeline event in
`review.timeline`.

> **Reviewers must NOT manually clear `staleReason`/`staleCode`.**
> Clearing an orphaned stale state is the pipeline's job: it happens only when
> the record is re-attached to a documented current source snapshot (or, for
> `source_changed`/`legacy_snapshot_unbound`, when a successful
> `applyReviewDecision` re-binds the record). Hand-editing these fields out of
> an orphaned record is treated as tampering: validation flags it, and
> `isEligibleForVerifiedDataset` still blocks the record.

## 4. Timeline events — immutable append-only history

Every `review.timeline` entry satisfies the `RecipeReviewTrace` shape:

```ts
{
  at: string | null;              // strict ISO date for human events, null for the pipeline
  actor: string;                  // reviewerId or "pipeline"
  action: string;                 // see list below
  status: RecipeVerificationStatus; // status AFTER the event
  note: string;                   // free-text rationale / reason
  evidenceIds: string[];          // evidence referenced by THIS event
  // Fingerprint fields — see below:
  sourceFingerprint?: string | null;   // human decisions only
  snapshotFingerprint?: string | null; // human decisions only
  previousFingerprint?: string | null; // source_drift_detected only
  currentFingerprint?: string | null;  // source_drift_detected only
}
```

### Action kinds

| `action` | Human or pipeline | Required fingerprint fields |
| --- | --- | --- |
| `imported_as_needs_review` | pipeline | (none; initial import) |
| `import_rejected_non_egyptian` | pipeline | (none; auto-rejection) |
| `curated_record_created` | pipeline | (none; reviewer-added record) |
| `migrated_from_legacy` | pipeline | (none; shape migration) |
| `migrated_cannot_bind_snapshot` | pipeline | `previousFingerprint=null`, `currentFingerprint=null` |
| **`human_verified`** | **human** | `sourceFingerprint` (64-hex), `snapshotFingerprint` (64-hex) |
| **`human_rejected`** | **human** | `sourceFingerprint` (64-hex), `snapshotFingerprint` (64-hex) |
| **`source_drift_detected`** | pipeline | `previousFingerprint` (old reviewed snapshot, or null for orphaned rows), `currentFingerprint` (newly computed row fingerprint, or null if the row was deleted) |

Invariants validated on every `npm run stage`:

- The latest `human_*` event's `actor` equals `review.reviewerId`, `at` equals
  `review.reviewDate`, `note` equals `review.rationale`, `evidenceIds`
  match (set-equal) `review.evidenceIds`, and `status` equals the record's
  current `verificationStatus`.
- The latest `human_*` event's `snapshotFingerprint` equals
  `review.snapshotFingerprint` (the immutable audit binding). Breaking this
  equality is a validation error.
- `human_verified` events must carry non-empty `evidenceIds`.
- `source_drift_detected` events must declare both
  `previousFingerprint` and `currentFingerprint` keys (null values are
  permitted for orphaned / deleted rows).
- `migrated_cannot_bind_snapshot` events must declare
  `previousFingerprint = null` and `currentFingerprint = null` — a legacy
  reviewed fingerprint is never fabricated.

## 5. Manifest-backed provenance and licensing (Step 2 review)

`data/manifest/sources.json` is the **sole** source of truth for source-file
provenance and licensing. A staged record NEVER carries a hand-written
`sourceVersion`, `accessDate`, `license.id`, `license.url`, or
`license.status=approved`; these fields are refreshed from the manifest on
every `npm run stage`.

For a `verified` record to pass the eligibility gate
(`isEligibleForVerifiedDataset` in `src/domain/recipes.ts`), the manifest
record for its source file **must** contain:

| Source review (provenance) | License review |
| --- | --- |
| `review_status: "approved"` | `license_review_status: "approved"` |
| `reviewed_by: <identity>` | `license_reviewed_by: <identity>` |
| `review_date: <strict ISO date>` | `license_review_date: <strict ISO date>` |
| `source_version` present | `license` identity string present |
| `access_date: <strict ISO date>` | `license_url` (http(s)) present |

The staging registry reflects manifest state as follows:

- No manifest record for the source → `license.status = "not_assessed"`,
  `source.sourceId = "<source file path>"`.
- Manifest record exists but is not yet approved → `license.status = "pending"`,
  manifest IDs are filled in.
- Manifest record fully approved (both source AND license) →
  `license.status = "approved"` and the record *may* become eligible once a
  human also verifies it culturally.

Transitioning the manifest from `pending` → `approved` immediately refreshes
the staged record's provenance and license fields on the next
`npm run stage` with no loss of history.

## 6. Reviewing a recipe (human only)

Reviewers either call `applyReviewDecision` programmatically (see
`src/domain/recipes.ts`) or edit `data/staging/recipes.json` to the same
effect. The resulting record must satisfy all validation rules or the next
`npm run stage` will report it as invalid.

1. Ensure the record is in `needs_review` (possibly via the drift/migration
   lifecycle below). For a fresh record the decision fields are clear
   (`reviewerId=null`, `reviewDate=null`, `evidenceIds=[]`,
   `rationale=null`). A record may legitimately be handed to a reviewer while
   still marked stale (`source_changed` or `legacy_snapshot_unbound`); the
   review is bound only when `applyReviewDecision` runs. **Do not hand-clear
   `staleReason`/`staleCode`** — the pipeline owns those. If the code is
   `source_deleted`, the record cannot be reviewed at all until the raw row
   is restored/re-attached (see §3).
2. Set `verificationStatus` to `verified` or `rejected`.
3. Set `review.decision` to match.
4. Set `review.reviewerId` (reviewer identity, e.g. `EG-RVW-<name>-<date>`).
5. Set `review.reviewDate` to a **strict ISO date** (`YYYY-MM-DD`, a real
   calendar date).
6. For `verified`: add the documented cultural‑evidence references to
   `review.evidenceIds` (manifest evidence IDs such as
   `EG-KOSHARI-CULTURAL-001` or published URLs) and summarize the evidence
   path in `review.rationale`. For human `rejected` verdicts, record the
   explicit rejection reasons in `review.rationale` (non-empty).
7. **Append** to `review.timeline` a `human_verified` or `human_rejected`
   event of the form shown in §4, including `sourceFingerprint` and
   `snapshotFingerprint` both copied from the current record's
   `sourceFingerprint`. **Never** delete or overwrite earlier entries; the
   timeline is append-only and preserves every reviewed fingerprint for
   later audits.

Evidence paths that count (from `MVP_REQUIREMENTS.md` §2.1):
E‑1 authoritative Egyptian source attribution; E‑2 approved Egyptian dish
registry match; E‑3 published cultural reference; E‑4 domain‑reviewer approval
based on documented evidence. Broad tags (Middle Eastern/Mediterranean/…) are
**not** evidence.

## 7. The verified‑MVP gate

A record enters the verified MVP dataset only when **all** hold
(`isEligibleForVerifiedDataset`):

- `verificationStatus = verified` (human decision, never automated);
- `review.decision = verified`, with `reviewerId`, strict‑ISO `reviewDate`,
  non-empty `evidenceIds` validated against `data/manifest/sources.json`,
  and non-empty `rationale`;
- `review.snapshotFingerprint` present (64-hex) AND `review.staleReason` is
  `null` AND `review.staleCode` is `null`/empty;
- `license.status = approved` AND backed by the manifest (§5);
- `source.sourceId`, `source.sourceVersion`, strict-ISO `source.accessDate`
  present;
- The source record itself is `provenance-approved` in the manifest (§5).
- Independent orphan block: even if a record's status/reviewer fields were
  tampered by hand, `staleCode = source_deleted` keeps it out of the verified
  dataset until the pipeline re-attaches it.

`npm run stage` reports the eligible count; any record failing these checks
is listed in per-record `blockers`. Unreviewed (`needs_review`), stale
(`staleReason`/`staleCode` set), manifest-unapproved, and auto-rejected records
are never eligible.

## 8. Drift lifecycle: source change → stale → re-review

When the raw source row backing a reviewed record changes (canonical columns
edited, row position deleted, or the row is otherwise orphaned) the next
`npm run stage` executes the deterministic drift protocol:

1. The reviewed `snapshotFingerprint` is compared against the freshly
   computed fingerprint of the raw row at the same position (or checked
   against all current fingerprints if the file shrank).
2. If they differ, `routeBackToReview` in `src/scripts/stage-recipes.ts` is
   called:
   - A `source_drift_detected` event is **appended** to `review.timeline`
     with `previousFingerprint = <old reviewed snapshot>` and
     `currentFingerprint = <new row fingerprint>` (or `null` if the row was
     deleted or orphaned). The exact old reviewed fingerprint is therefore
     preserved forever in the history.
   - The record's status is reset to `needs_review` and all human decision
     fields are cleared (`reviewerId`, `reviewDate`, `evidenceIds`,
     `rationale`), so the record looks structurally identical to a freshly
     imported pending record.
   - `review.staleCode` is set to `source_changed` (row edited) or
     `source_deleted` (row deleted/orphaned), and `review.staleReason` is
     set to a matching descriptive string.
   - Machine-owned fields are refreshed to the new snapshot when available:
     `original`, `sourceFingerprint`, `sourceVersion`, `accessDate`,
     `source.url`, `license`.
   - After the event is appended, `review.snapshotFingerprint` is set to
     `null` — the old snapshot has been preserved in the
     `source_drift_detected` event, and the cleared field forces the next
     human re-review to re-bind via `applyReviewDecision` to the **new**
     fingerprint.
3. `staleCode`/`staleReason` blocks eligibility (§7). The record now waits for
   human re-review.
4. **Orphaned rows are not reviewable.** A record with
   `staleCode = source_deleted` is rejected by `applyReviewDecision`
   (`ok:false`) and blocked by the eligibility gate even if its status and
   reviewer fields are manually tampered to look `verified`. When the raw row
   is restored (or the record is attached to a documented current source
   snapshot), the next `npm run stage` re-attaches the record, refreshes its
   machine-owned fields, and downgrades the code to `source_changed` so a
   legitimate re-review can occur.

On re-review the reviewer applies `applyReviewDecision` exactly as in §6,
and the resulting `human_*` event captures the *new* source/snapshot
fingerprints alongside reviewer/date/evidence. `staleReason` is cleared.
Both the v1 review, the drift event, and the v2 re-review remain side-by-side
in `review.timeline` for a complete provenance audit trail.

## 9. Validation

`npm run stage` runs strict validation over the whole registry and exits
non‑zero on: duplicate `recipeId`s, missing source references, invalid
statuses, mojibake/blank names, invented zeros (`servings`/`finalCookedWeightG`),
malformed or non-SHA-256 fingerprints, broken fingerprint/timeline
bindings (§4 invariants), **unverifiable** records (e.g. `verified` without
reviewer/date/evidence), and when **no recipe is eligible for the verified
MVP dataset** (blocker, `0` eligible — nothing is fabricated to reach a
target). Every fingerprint must be exactly 64 lowercase hex characters;
uppercase, short/long strings, and arbitrary non-hex strings are rejected.

## 10. Traceability summary

- `original` preserves the verbatim raw header → value map of the imported
  row (requirement: never overwrite original source values).
- `sourceFingerprint` cryptographically binds that raw row (via its
  canonical columns) to the staged record.
- `review.snapshotFingerprint` binds a human verdict to the exact reviewed
  snapshot (copied from `sourceFingerprint` at decision time).
- Every `human_*` timeline entry carries the fingerprints that were on the
  record at the moment of review, plus the evidence IDs used.
- Every `source_drift_detected` timeline entry carries the
  *previous* reviewed fingerprint and the *current* raw fingerprint (or
  nulls for orphaned/deleted rows) so that the sequence “v1 reviewed → row
  changed → v2 re-reviewed” is fully auditable without having to keep old
  versions of the raw CSV.
